# 文档模板 (Phase 2.6)

proj-doc-builder v4.0 使用以下模板。Agent 在 Phase 2 生成文档时应严格遵循。

---

## 文件清单铁律

> **所有模板共通的强制性规则——违反即质量门控失败。**

1. **每个文件都必须列出**：源码目录中的每个直接普通文件在表格中恰好一行。
2. **"关键内容"列禁止泛化**：严禁写"Python 源码"、"文件资源"、"杂项文件"等无信息量描述。
   - Python 文件：列核心 class / function 名称与签名（通过 AST 提取）
   - YAML/JSON 配置：列顶层 key 与用途
   - Markdown 文档：列文档主题
   - 头文件（.h）：列核心宏定义、结构体或函数声明
   - C 源文件（.c）：列核心函数名
   - 二进制/不可读文件：注明"非文本文件，未自动分析"
3. **文件计数一致**：概述中提到的文件数必须等于表格行数。
4. **按文件名字母序排列**。
5. **空目录降级**：如果源码目录为空（0 个直接文件且 0 个子目录），文档必须使用 placeholder 模板。

---

## 概述铁律

> **概述是文档的信息密度核心——AI 和人类读者首先看的就是概述。**

1. **禁止模板套话**：严禁使用以下泛化句式（自动检测黑名单）：
   - "本目录（X）是 V4 工程中 X 模块的组成单元，承载对应的实现或数据"
   - "构成该单元的主体内容"
   - "该单元与工程内相邻模块通过既有接口与文档契约交互，服务算法对通与测试回归目标"
   - "下辖 N 个子目录，覆盖相关主题域的细分实现"
2. **三要素必须真实**：
   - 定位：目录在工程架构中的确切位置与角色（不是"组成单元"）
   - 内容：核心文件/符号/数据的具体名称（不是"实现或数据"）
   - 依赖：上下游关系的具体模块名与接口（不是"既有接口与文档契约"）
3. **信息密度要求**：概述至少包含 2 个具体实体名称（类名、函数名、标准编号、配置 key 等）。
4. **父目录概述**：如果目录无直接文件、只有子目录，概述必须列出各子目录的文件计数与核心职责。

## 概述

<3-4 句话的高信息密度实质描述，包含三要素：
1. 输入源：从哪些模块/数据源接收何种格式的数据；
2. 核心处理与时效：执行的核心算法、并发模型或处理周期/延迟约束；
3. 下游交付：向下游产物或调用方交付何种数据结构与业务契约。
严禁使用"负责承担...的关键业务逻辑与基础设施功能"、"提供规范化的接口抽象"等泛化空话套话。>

## 文件清单

| 文件 | 用途 | 关键内容 |

## 关键符号

<仅 Python 包（有 __init__.py）的目录才需要此节。必须通过 AST 真实性核验，严禁虚构不存在的符号。>

| 符号 | 类型 | 定义位置 | 说明 |
|------|------|---------|------|
| `ClassName` | class | `<file>.py:L行号>` | <核心能力说明与对外核心方法签名，如 `def run(self, ctx: Context) -> Result`> |
| `function_name` | function | `<file>.py:L行号>` | <函数签名与核心业务用途，如 `def calc(v: float) -> float`> |

<≤10 文件的叶子目录：列出全部符号。>10 文件：列出最重要的 10 个。父目录：列出各子模块暴露的公共接口。>

## 系统角色

<详细说明该目录在整个项目架构中的位置与数据流向。推荐附带极简 ASCII 数据流图：>

```text
[上游数据源/模块] ──(输入契约)──> [当前模块核心处理] ──(输出契约)──> [下游消费模块]
```

必须包含以下至少一项：
- 在系统分层架构（如 L0~L6）中属于哪一层，上下游交互约束
- 核心处理模式（如快慢双轨解耦、原子事务、事件流总线）
- 确切的数据输入源与输出流向

### 变体

**叶子目录**（无子目录）：省略"子目录"节。
**边界目录**（含自身 CLAUDE.md）：概述末尾追加 `> **边界目录**：本目录有独立的 CLAUDE.md，此处仅列概要。`，不递归进入子目录。
**纯 C 头文件目录**（无 Python `__init__.py`）：省略"关键符号"节，但在文件清单的"关键内容"列中列出核心宏定义、结构体名或函数签名。
